# Hazard prediction: proof of concept and evaluation proposal

Status: **draft for team review**. This document describes the implementation on
`feat/hazard-tabpfn` and proposes how to evaluate it. Proposed experiments have not
been run unless explicitly identified as results.

For a presentation-friendly explanation and reproducible figures, see
[RESULTS_GUIDE.md](RESULTS_GUIDE.md).

## Purpose and scope

The prototype explores whether a tabular foundation model can turn an estimated
leak location and wind into a map of possible gas hazards. It is part of a larger
simulated workflow: sensor readings -> source estimate -> hazard map -> evacuation
routes. It is not a real-factory safety system and has not been validated on real
gas measurements or an independent dispersion simulator.

Suggested pitch language:

> We built a proof of concept that predicts simulated hazard maps from an estimated
> gas leak and uses those maps to explore evacuation planning. Our initial results
> are limited to a simplified simulator; independent simulation and real-data
> evaluation are planned.

## Current data and implementation

- **Data source:** `sim/` generates the factory, leak scenarios, gas concentration
  fields and noisy sensor readings. No external factory dataset is used. The
  concentrations and hazard thresholds are relative simulator units, not measured
  concentrations for a specific gas.
- **Factory:** the default layout is a 600-cell, two-dimensional grid with walls,
  machines, sensors and exits. The simulation uses simplified gas dispersion and
  one wind vector for the whole layout.
- **Training examples:** `library.training_rows` samples simulated leaks, cells and
  early decision times (5-60 s) and forecast horizons (0-120 s). A source locator
  estimates a map from readings available by the decision time; a top-three source
  hypothesis is sampled using its weight, and the wind comes from noisy readings.
  The target remains the true concentration from that simulated scenario. The
  default locator is the weighted-centroid baseline; `fit(source_locator=...)` can
  instead use an already-prepared locator, potentially incurring its inference cost.
  `features.cell_features` describes each cell using downwind and
  crosswind displacement, distance, time, wind speed, release rate and the fraction
  of sampled points along the source-to-cell line that lie on open floor. The
  target is the simulated concentration at that cell and time. The current default
  context seed is 1001; the original three-episode result below used seed 42.
- **Model:** `TabPFNHazardPredictor.fit` gives those examples to the shared
  `make_regressor` interface. The cloud backend uses a pretrained TabPFN model;
  it does not train a foundation model from scratch.
- **Prediction:** `predict` takes measured wind and a `SourceEstimate`. It builds
  rows for the most likely source cells, predicts all requested cells and times in
  a batch, converts predicted concentration quantiles to toxic and flammable
  probabilities, and mixes them by the selected source probabilities. Fire is
  restricted to ignition cells. Individual gas sensor values do not currently
  appear as hazard features; they influence the source estimate upstream.
- **Optional experiments:** `include_geometry=True` adds four-neighbour open-grid
  path length and reachability as features. This is a geometric proxy, not a gas
  flow model. `source_mass` optionally chooses enough source cells to reach a
  desired probability, up to `top_k`; `last_selection` records retained mass and
  whether the target was reached, and a missed target emits a warning. Defaults
  remain the original features and top three cells with no probability target.
- **Optional request splitting:** `ChunkedRegressor` can wrap a regressor to limit
  prediction rows per request. It is not enabled by default; each chunk is a
  separate cloud request and may incur its own charge.
- **Optional open-cell queries:** `open_cells_only=True` skips querying solid grid
  cells and fills them with zero in the returned maps. This preserves the output
  shape. Cloud results can vary with query batching; the small comparison below
  does not establish a general latency or accuracy improvement.
- **Integration:** `uv run leak-demo` still uses the original source and hazard
  baselines by default. The comparisons with Rayan's locator used an isolated
  copy of his branch; they have not changed or merged his code into this branch.
- **Baseline:** `ForwardSimPredictor` chooses the single most likely source,
  uses measured wind and the estimated median release rate (or 1.0), runs the
  same simulator and thresholds the concentrations to produce 0/1 probabilities.

Both approaches are evaluated against truth generated by the same simulator.
This can test the workflow and compare behavior under its assumptions, not show
that the predictions generalize to an actual facility.

To reproduce the Rayan-locator experiments, make an isolated checkout containing
this hazard branch and the source code from Rayan's recorded commit; run
`tests/hazard/compare_source_maps.py` with explicit `--run-cloud` and an output
path outside the repository. Supply that generated synthetic `.npz` file with
`--input` to the selection, geometry or cache scripts, each of which also requires
explicit `--run-cloud`. The example data is generated rather than committed;
quote costs again before rerunning because model availability and prices can change.

## Known limitations to review

1. Context examples now pair a sampled source estimate and measured wind with the
   true simulated outcome. The default centroid locator is a proxy for the live source
   model; its errors and source-map shape may differ from Rayan's model. Drawing an
   estimated source and then mixing source-conditioned predictions is an empirical
   approximation; calibration and comparison against true-source-conditioned
   examples remain important. Rate falls back to 1.0 unless the locator returns it.
   Old results below used true source, true wind and true rate in training; they do
   not measure the revised context generation.
2. Only the top source cells are retained and their weights are renormalized;
   probability outside those cells is dropped. The default is three cells.
3. Conversion from quantiles to threshold probabilities interpolates between
   quantiles and assumes probability 0 or 1 outside their range. This can produce
   overconfident probabilities; calibration has not been established.
4. The shared pipeline combines toxic and fire probabilities as independent even
   though, for the current thresholds, flammable gas is also toxic. This can
   overstate harm. The shared pipeline is integrator-owned.
5. The factory, airflow, sensor model and relative thresholds are simplified.
   Real sensors, gas-specific effects, ventilation and vertical variation are
   not validated here.
6. The preliminary training seed was 42. The team data guide proposes reserving
   seeds 0-99 for shared evaluation and using seeds >=1000 for training. The
   preliminary evaluation used a different seed, 0, but the training seed does
   not follow that proposed allocation.
7. Different seeds give different random scenarios, but may still sample the same
   leak sites. This experiment does not establish generalization to a new factory.

## Results already observed

### Early alarms on the proposed pipe simulator

The following is a separate experiment from the older results below. An isolated
copy of Steven's proposed sync branch (PR #28, head `d124666`) supplied pipes and
the live walker; our uncommitted hazard code was overlaid for the comparison.
The PR stack was not merged into this branch. Thirty default-plant pipe leaks,
evaluation seed 0, were paired across models; the clean simulated detector set
the alarm (median 10 s), readings were noisy, and the weighted-centroid locator
provided the same source map to both predictors. The centroid does not enforce
the pipe prior and is not Rayan's locator. The hazard context used seed 1001,
100 simulated scenarios, 20 cells, four sampled horizons, sampled centroid source
hypotheses and measured wind; TabPFN used the top three source cells.

The same temporary checkout passed the `sync-check` CLI's 24 offline cases
(two plants, decision times 10/20/30/60 s, three seeds), with no hard problems.
The default centroid source generated two warnings: probability outside pipe
sites and no estimated release rate. The offline k-NN query chunk was set to 128

### How much source probability is retained?

An offline diagnostic ran the **existing weighted-centroid source baseline** on
30 default-factory scenarios, evaluation seed 0, with 30 sampled people and the
pipeline's 60-second sensor-reading setup. Cloud credits spent: 0 for both source
selection approaches below. This does not evaluate Rayan's TabPFN locator.

| Diagnostic | Top 3 cells | Highest-probability cells covering at least 90% |
| --- | ---: | ---: |
| Mean probability retained | 7.06% | At least 90% by construction |
| Mean cells selected | 3 | 83.4 |
| True simulated source included | 1 / 30 | 22 / 30 |

Top-three retained mass ranged from 5.89% to 9.33%; the 90% selection needed
49 to 109 cells. The true source was also the single highest-probability cell in
1 / 30 cases. These are descriptive results on a small set of simulated cases,
not a measurement of TabPFN forecast quality or proof of calibration. The larger
selection has not been used with the TabPFN hazard predictor.

This result makes the top-three truncation worth investigating before claiming
that it captures the source map's uncertainty. The benchmark described above used
the weighted-centroid locator, not Rayan's TabPFN locator. The following
comparison measures both on the same simulated scenarios.

### Offline diagnostics: geometry and source selection

Two reproducible, offline diagnostics explore the limitations without API calls:

```bash
uv run python tests/hazard/diagnose_geometry.py
uv run python tests/hazard/diagnose_source_selection.py
```

**Geometry counterexample.** Two synthetic 14 m x 10 m factories have the same
source, target, wind, leak rate and wall between source and target. The door in
that wall is near the source-target line in one layout and farther away in the
other. At 120 s, both produce the identical seven-feature row for the target,
but the simulator reports concentrations of 0.13408 vs 0.00882 (near vs far
door). The relative toxic threshold is 0.1, so the simulator marks that target
toxic in the near-door layout and non-toxic in the far-door layout. The rate
was chosen to expose this distinction. This constructed example demonstrates
missing information in the current features within this simulator; it does not
quantify how often the issue occurs or validate the simulator against reality.
It does not run or assess a fitted TabPFN model.

**Optional geometry feature, evaluated on the default factory.** The experimental
`include_geometry=True` adds open-grid shortest-path distance and reachability
to the original seven features; it uses four-neighbour movement. It is a proxy
for layout connectivity, not a gas-flow equation. The default remains unchanged.

On the same 30 default-factory episodes and Rayan source maps described above,
compare the forward baseline with TabPFN using either the original features or
the optional path features. Both TabPFN variants used the same 8,000 simulated
context examples (seed 1001), the same top-three sources, measured wind and rate
fallback 1.0. Toxic scores are pooled over open cells at 70-180 s; evaluation
scenarios use seed 0. Source locator context used seed 12345. The cloud model
version and fit mode were not explicitly selected.

| --- | ---: | ---: | ---: |
| Toxic Brier, lower is better | 0.04638 | 0.05832 | 0.05600 |
| Toxic ECE, lower is better | 0.04638 | 0.03397 | 0.03450 |
| Toxic AUC, higher is better | 0.91150 | 0.95749 | 0.96200 |

The original vs path-feature paired mean Brier difference (path minus original)
was -0.00233, with an exploratory episode-bootstrap 95% interval from -0.00413

Each cloud variant made 30 quoted 10,000-credit predictions; account usage rose

`compare_source_maps.py` plus explicit `--run-cloud`; rerunning spends credits.

**Source-selection diagnostic.** On the same 30 simulated cases and source maps
described above, compare two *simulator-based mixtures*: weighted concentration
thresholds for the top three sources vs the smallest set covering at least 90%
of the source probability. Both use measured wind, rate 1.0, the same scenarios,
and are scored against the true simulated toxic outcome on open floor at forecast
times 70-180 s. The mean toxic Brier score (lower is better) was **0.09288** for
top three vs **0.07345** for the 90% selection. The latter scored lower in 28 of
30 episodes and higher in 2. It used 83.4 candidate sources on average vs 3;
both methods spent 0 cloud credits.

This is a controlled comparison of selection strategies using forward simulation
for both, not an evaluation of TabPFN or Rayan's locator. It supports investigating
source truncation, but does not establish that the 90% choice improves the current
TabPFN predictor or justify its runtime or API cost. Both methods and the truth use
the same simplified simulator, and 90% is a chosen test setting, not a validated
optimal cutoff.

The evaluation used five default-factory episodes, seed 0, weighted-centroid source

The cloud model version and fit mode were not explicitly selected or recorded.

| --- | ---: | ---: | ---: |

The offline model had a higher average Brier score than cloud TabPFN on this

Reproduce only after reviewing cost and opting in explicitly:
`uv run python tests/hazard/compare_backends.py --run-cloud`. This sends synthetic

### Cache and Fast-model experiment

An initial cache attempt with 21,600 test rows failed: the service reported a
10,000-row limit per cached prediction request. Splitting the forecast into
10,000 + 10,000 + 1,600 rows produced successful predictions using the optional
`ChunkedRegressor`. The configured cache mode and server metadata on the last
chunk of each successful forecast indicated a cache hit; metadata for the other
chunks was not independently retained by the script.

The following is a small timing experiment on five of the same 30 simulated
episodes (seed 0, Rayan source maps), using the original seven hazard features,
top three sources, and the same 8,000 context rows (seed 1001). Model versions
and eight estimators were explicitly selected. Times cover the hazard call,
including features, quote requests, network and prediction; they exclude the
source locator and fitting. Each model was fitted once, and model call order was
rotated across cases. Forward Brier for these same five cases was 0.04405, with
zero cloud credits.

| Cloud configuration | Toxic Brier (lower better) | Median hazard time | Credits / forecast |
| --- | ---: | ---: | ---: |
| v3.5, preprocessing only | 0.07029 | 3.65 s | 10,000 |
| v3.5, KV cache, 3 chunks | 0.07034 | 4.68 s | 30,000 |
| v3.5-Fast, preprocessing only | 0.06827 | 2.74 s | 10,000 |
| v3.5-Fast, KV cache, 3 chunks | 0.06825 | 4.32 s | 30,000 |

Single observed fit times were 4.24 / 3.71 s for v3.5 without / with cache,
and 82.78 / 82.84 s for Fast without / with cache. Service waiting time varied,
so these single setup observations should not be generalized. The successful
comparison incurred 400,000 credits in total, matching both account usage change
and quotes. The preceding unsplit test completed ten non-cached predictions for
100,000 credits; its two failed cached calls and one failed diagnostic retry had
no additional charge observable in the account usage checks. The guard increments
its quoted counter before a call, including failed calls, so its counter is not
itself proof of actual billing.

The maximum observed per-cell toxic-probability difference between the cached
and non-cached runs was 0.03560 for v3.5 and 0.03423 for Fast. Both caching and
batch splitting changed between those conditions, so this experiment cannot
attribute the difference to either one. This is not enough evidence to assert
that cached and non-cached hazard forecasts are numerically interchangeable.
With just five cases and variable cloud service times, the results are indicative
only. The Fast variant may be worth further testing, but this run does not show
a validated accuracy or real-time guarantee. Reproduce with
`tests/hazard/compare_cache_fast.py` and explicit `--run-cloud` plus the temporary
synthetic inputs; rerunning incurs credits.

## Evaluation design and remaining work

The aim is to measure this proof of concept on its own terms, using paired cases
and recording enough detail to reproduce the results. Some comparisons above
address parts of this plan; remaining decisions are marked below.

1. **Freeze settings.** Record the commit, simulator version, layout, sensor noise,
   time horizon, model and backend, training size, source locator, `top_k`, and
   release-rate policy. Pin or record the cloud model version and fit mode. Use a
   training seed >=1000 and a separate evaluation seed from the team's reserved
   range; say explicitly that the same leak sites can still recur.
2. **Choose the conditioning design.** Keep source-conditioned context examples
   as the reference design and measure how the source map is used. Evaluate the
   effect of uncertain wind and rate. Alternative context designs, if considered,
   must be tested rather than assumed to improve the model; adding source noise
   while also mixing source probabilities could change how uncertainty is counted.
3. **Pair the scenarios.** Run the baseline and TabPFN predictor on the same leaks,
   people, noisy readings, source estimates, forecast times and truth. Neither
   predictor receives the true source or wind at prediction time. If an oracle
   comparison is added, label it separately because it has extra information.
4. **Measure forecast quality.** Report toxic Brier, ECE and AUC; state the grid
   mask, times and averaging method. Include an open-floor-only analysis so wall
   cells cannot obscure the result. Report per-episode paired differences and a
   measure of uncertainty where the sample size supports it. AUC is undefined
   if only one outcome class occurs. Treat the existing combined-harm metric as
   provisional until the shared combination issue is addressed.
5. **Measure runtime.** Use a monotonic clock to time training-data generation,
   model fit, per-episode feature construction and prediction, and total pipeline
   time. Report cold and repeated calls separately, the number of runs and a
   suitable summary, plus the same relevant timings for the forward baseline.
   A 60-second observation window is not model runtime. The current benchmark
   does not collect these timings; instrumentation is required first.
6. **Record cost and availability.** Quote the intended call sizes before a cloud
   run. Record the actual usage change where possible, the per-call quotes, failed
   calls and total. The guard counts accepted quotes, not verified final billing.
   Record network/cloud dependence. Any larger run requires an agreed budget.
7. **Compare cache settings only as a separate experiment.** Hold data, model
   version, settings and scenarios fixed while comparing the default fit mode
   with explicit KV caching, if supported. Measure fit time, repeated prediction
   time, output differences and credits. Do not assume the cache is active or
   faster for this workload without measuring it.
8. **Investigate source-map truncation.** Compare top-three, adaptive retained
   probability and other practical selections on the same maps and episodes. Report
   retained mass, source coverage, downstream hazard quality, runtime and credits.
   Set any maximum number of source cells explicitly and report when that cap
   prevents reaching the intended retained mass. The optional `source_mass` and
   `top_k` cap now expose this choice and warn when the target is not reached;
   the paired comparison above is preliminary evidence, not a final policy.

The current `benchmark.py` runs paired episodes and reports the metrics in the
table, but it hard-codes training seed 42 and does not implement the full protocol
above. Do not interpret this proposal as an already executable command.

## Later iterations

After documenting this proof of concept, evaluate whether an independent
dispersion model can provide suitable matching inputs and truth. A Gaussian puff
may provide a controlled, simple comparison, while GADEN may offer a more detailed
3D environment; the model and experiment have not been chosen. For a 3D source,
a carefully specified horizontal slice is one possible way to compare with the
current 2D interface, but loses vertical information. Finally, choose real data
whose sensor inputs and labels support a specific test. Each stage supports claims
only for the conditions and measurements actually evaluated.
